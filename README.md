# StructureAnalysisEnvironment(仮)

<p>VASP, WIEN2k, Quantum ESPRESSO, OpenMX, CP2K, GPAW, HiLAPW, FDMNES, RMC_POT 等の第一原理計算および逆モンテカルロ法の各種計算コードに対応した入出力・解析の一元化を目指した統合環境フレームワーク。これにより、計算コードの違いを意識することなく、構造作成や解析などの計算コードの入出力・解析を統一的な方法で実現できます。およびそのフレームワークを用いて開発された実用的なツール群。

## 特徴
<p>各種計算コードの入出力の変換機能がメインとなります。たとえば、構造の変換に限ってみれば、結晶・分子構造をその計算コードで要求される形式に変換するだけではなく、その他計算に必要な入力項目の変換も含んでいます。基本方針としては、変換後にはある程度そのまま無編集で計算まで持っていけることなど、計算コードの入出力に関して、可能な限り計算コードの違いを吸収することを目指しています。計算コードを扱う際の入出力の一元化に関しては、当然計算コードのアルゴリズム上、本質的に同じように扱うことが無理な場合も多数あります。その場合は、ある程度は私自身の推奨する独断と偏見の初期パラメーターを与えて簡略化をしています。当然詳細設定も可能です。無論、最初から一元化を諦めて特化機能としている部分も多数ありますが、これらはほぼ同じ手順で簡単に操作が可能です。

### フレームワーク
<p>中間ファイルは可能な限り吐き出さず、すべてPythonのOOPモデルで書かれており、フレームワーク上で一元的に処理しています。この手の統合環境では中間ファイルを積極的に用いる開発方針もあるとは思いますが、小谷先生流にかっこ良く言えば<B>「計算のための独自言語」</B>を設計していますので、本フレームワークでは当然、中間ファイルは一切用いません。近代的な意味での（それもカビが生えていますが）一般的なフレームワークをデザインしています。もっとぶっちゃけると関数とクラスの集合体でしかありません。エンドユーザーから見るとおそらくこのフレームワークは全く意味を持たずに、私自身がこのフレームワークを用いて開発したツール群が実態として意味を持つことになるかと思います。また、第三者がこのフレームワークを用いて開発することは現時点ではお薦めしません。普通にASEを用いて開発したほうがはるかに有意義です。

### マイナー対応
<p>一部国産コードや逆モンテカルロなどのマイナーコードや、pCOHPなどのマイナーな解析出力に対応しているのが実用上の特徴かと思います。RMCへの対応は業界初だと思っています。また、わりとXANES関係には力を入れていますのでそっちの業界の人には結構役立つと思います。OpenMXやRMCを除き、対応している第一原理計算コードはすべてXANESスペクトル計算が可能であり、その意味ではこのフレームワークは<b>XANESスペクトル計算統合環境フレームワーク</b>であるとも言えます。実際、開発の主目的もほぼXANESスペクトルの解析です。微妙に実現しているとは言いがたいですが、割と便利だと思います。

### 解析対応
<p>電荷密度、局所状態密度、バンド分散、Barder電荷、XANESスペクトル、pCOHP解析などを始めとした、基本的な計算ログのだけではなく、様々な計算の解析・プロット、およびそれらへの入力支援を行う機能を多数含んでいます。開発者自身の開発のモチベーションの主軸はむしろ解析支援部分の機能の開発にあります。

### 構造作成支援
スーパーセルの作成から配位数やボンドのサーチ、指定した局所構造の並進移動などの座標のモディファイ、表面作成や真空層作成なども含みます。わりと構造系の支援はしてくれるクラスや関数は作っているのですが、現時点ではあまり賢く作ってないのと、機能もまだまだ不十分です。ASEのようにナノパーティクルとかナノチューブとかは自動では作ってくれません。

### 2Dプロット機能
<p>2Dプロット機能は基本的にはmatplotlibモジュールを用いていますので、PDF/EPS出力に対応しています。局所状態密度解析などを初めバンド計算で用いられる一般的な解析のテンプレートはすべて実装しており、かなり容易にルーチンワークに持っていけると思います。スクリプトからの自動実行・ルーチン作業化が大前提ですので、GUI化には全く力を入れておりません。当然バンド分散プロット等では波動関数成分の可視化をE-Kプロット上に連続的な色の変化やポイントのサイズの変化で同時に表示することにも対応しています。また、VASPの一般的な可視化ソフトであるp4vaspのXML形式へ各種計算コードの結果を変換する機能を持っているのがおそらくマニアックな特徴となります。p4vaspでアニメーションもします。XCrysDen にはまだ対応してません。小口先生のPSP形式の対応はこっそりとは進んでいますが、maplotlib 機能で直接PDF出力したほうが現時点では健全です。

### 3Dプロット機能
<p>3Dプロット機能およびGUIはほとんどおまけといいますかまだ機能テストの段階でして VPython + wxPython を用いています。そのうちVTKの利用や直接OpenGLを用いることを検討していまして、現在一部機能は準備中です。ただ、実際問題、開発リソースが１人で、しかも内職ですので全く構想に開発が追いついていません。現段階では、役立ち機能では Barder 解析の結果を可視化するあたりは役に立つ3Dプロット機能は実装したとは思っています。それ以外では、出力結果をVESTA/p4vaspで描画したほうが現時点ではまだマシです。


## 開発の経緯と現状
元々は作者が大学院時代からポスドク時代までのおよそ１５年位の間にほそぼそと個別に作っていたAWK/Perl/Cなどを用いた多数の変換・プロット・解析支援プログラムがベースになっています。これまで、それぞれの支援コードにおいて、各支援コードが同じような方法論で使えるインターフェースを持ちつつ、それぞれの支援コードが相補性的に機能するように作ってきましたが、対応する計算コードの増加と、開発規模の肥大化に伴い、全体像としての開発が破綻しかけていたのがまず現状としてあります。そのため、自身の利便性と趣味でPython化したことから始まっています。フレームワーク化により多くの問題は解決されます。Pythonでフレームワーク設計ですので、ASEをご存じの方は、ASEを思い出すと思いますが、本コードは結果的にはASEの廉価版だと思ってくれてよいです。機能も実装技術もかなり廉価版です。開発当初は自身の不勉強のためにASEの存在をあまり良く知らなかったこともありますが、Python フレームワークで計算の統合環境といえば、ASEがダントツで優れており、業界標準です。欧米では第一原理計算コードはASE対応が前提なものがほとんどです。おそらくASE以外にはそれに匹敵する同等のツールは必要ありません。開発の無駄です。

<p>一応、このフレームワークの意義は、自身の利便性のための自身のためのコードでして、その意味ではASEとは別の価値があるとは思いますが、実質的には機能の大半はASEと同等のことをしています。当然、ASEの方が高機能です。一応ミソとしてましては、ASEで対応していない国産のマイナーコードやマイナーな解析に対応している特徴はあります。さらに、自身の利便のために可視化も含めて様々なツール群を作っていまして、おそらくユーザーの視点で見るとフレームワークというよりはフレームワークとともに配布するツール群には一定の価値は見出していただけると思います。当然、それでも、同等のツールはメジャーなコードにはそれぞれあるとは思います。

<p>同じく、マイナー対応では小谷先生が、同じくPythonフレームワークでXtalEditを開発されてまして、そちらの方が国産コードの対応が進んでいますが、開発は停滞しているようです。やはり Python を使った計算シミュレーション系の統合環境フレームワークは、結果的には老舗であるASEを追いかけ、その廉価版になってしまうのは必然かもしれません。おそらく、自己満足以外の目的では、計算物理屋は自身でこのようなコードを開発せずに、マイナー機能やマイナーコードの対応クラス等が欲しかったならば、ASEへ何らかの形でをコントリビュート、ASEからのブランチとしたほうが健全ではないかと思っています。

### 現状と未対応状況
<p>現状では、作者自身が一部の人に配布していた、AWK/Perl/Cなどの各種コードを用いた古い解析・計算支援系コードのうち、特に、KANSAI-92、LmtART、MarkさんのLMTO、FHI-AIMSなどへの対応した機能は、現時点では全くフレームワークへの移植・対応はしておりません。その他VASPなどのコードにおいても、まだ一部の機能しか実装できていない問題があります。

<p>最大の問題は、統合的なフレームワークのデザインで未だに自身の方針が二転三転しているのと、自身のスキルなさと、そのスキルの変遷、特にOOP デザインへの理解度の変遷が、コードのリファクタリングにまったく追いついていません。そろそろきちんとリファクタリングしないと開発が発散してしまいそうで、少し限界に近い状況でもあります。そのうえ、いまだに対応するコードや機能が増加中で、あらゆる開発が追いついていないのが現状です。

### 名前
<p>ネームスペースを作る都合、現時点ではStructureAnalysisEnvironment (SAE) と名づけていますが、ASE (AtomicSimulationEnvironmet)の存在を知る前につけたネーミングでして、今の実感だとこの前はこの名前は<B>ありえない</B>と思っています。自身でもASEと混乱します。そのうち変更予定です。現状の名前はあくまで（仮）です。

### ASEモジュールおよびcif対応
<p>残念ながら現状では、群論に関するごく一部機能をASEのルーチンから用いています。ASEに慣れてくると自身のフレームワークの存在価値を失いそうになるのですが、一応、これら群論機能の独自実装は一部では進んでますのでそのうちフレームワーク本体からのASEモジュールの使用は除きます。ただ、時間が足りていないのとぶっちゃけ、ASEモジュール利用で困ってないので、困っています。その他、現状では私のフレームワークでは直接 cif の読み書きは直接できないので、この機能を ASEモジュール に頼るか PyCifRWモジュールに頼るか、中途半端な独自実装をするかは迷ってます。cif変換系はASEのフレームワークを使う支援プログラムとして、ツール群の中に一緒に放り込んではいますので、ユーザー視点としてみれば、実用上は問題無いとは思います。一般にはcifからの変換系ツールでは [cif2cell](http://sourceforge.net/projects/cif2cell/) が対応フォーマットの多さと利便性と知名度で何歩か進んでいると思います。cif2cell だと当然彼らも独自実装せずに、PyCifRWモジュールで対応してます。ともあれ、正直cifに関しては、VESTAを一度通せばほとんど対応できるので実際問題微妙にモチベーションは低いです。

### 今後
<p>群論機能の充実とバンドフォールディング機能の実装などは目論んでいます。それも [unfolding](http://www.ifm.liu.se/theomod/compphys/band-unfolding/)  コードを別途見つけてしまったのでいささかモチベーションが低いですが、コード自体の大規模なリファクタリングを含めて、趣味で取り組んで行きたいとは思います。何回かリファクタしたあと PyPI に登録とは目論んでいます。この手のコードは、ASE が世の中にある現場、<b>マイナーの計算コード対応</b>と、<b>独自の解析機能実装</b>と、<b>GUI機能の充実</b>以外ではおそらくオリジナリティと利便性は出てこないと思います。開発の意義は多分それです。できれば、ASEにもkコントリビュートとしたいとは考えています。また、当然、多くの実験屋に使ってもらう意味ではGUIの充実は必要不可欠かと思いますが、正直１人の内職では高度なGUI開発は時間がしんどいです。なにより個人的にGUIがなくてもまったく不便に思ってないのが大きいです。Windows中心ならばC++でGUIを作るべきかとも思ってまして、wxWidgets クロスプラットホームとも思っています。趣味で少しずつリハビリを兼ねて開拓中です。結局、どれに時間と力を注ぎこむのかは今後次第ですが、しばらく計算をする仕事からは離れそうなので、あまり開発は進められない気もします。

## フレームワークを用いたツール群の解説

### 基本ルール
普通ユーザーはフレームワーク自体を直接使うことはほぼ稀となります。実際には、ユーザーはフレームワークとともに提供されるツール群を用いることになります。このツール群は、一部の例外はありますが、基本的には以下のルールに則ってネーミングをされてます。

1. <b>大文字</b>から始まるコードはユーザーが編集する必要のない<b>汎用ツール</b>。非常に多くのコマンドラインオプションを持ち、かなり高機能化、肥大化しているツールもあります。大抵は -h でヘルプが一応出るようにしてます。汎用の高機能のマクロです。

2. <b>小文字</b>から始まるコードはユーザーがその都度必要に応じて直接編集する必要があります。ただし、実施問題小回りの効いた非常に小さいコードであり、Pythonおよびフレームワークをを知っていれば汎用性が高く、ある意味一番便利なコードでもあります。一種の野良マクロです。

3. 先頭の<b>大文字</b>もしくは<b>小文字</b>は使用する計算コード（もしくは使用するフレームワーク)を示します。
	1. <b>AS</b>から始まる AS\*.py プログラムは <b>ASE</b> を用いた変換系コード
	2. <b>CP</b>から始まる CP\*.py プログラムは <b>CP2K</b>用
	3. <b>FD</b>から始まる FD\*.py プログラムは <b>FDMNES</b>用
	4. <b>LA</b>から始まる LA\*.py プログラムは <b>HiLAPW</b>用
	4. <b>MX</b>から始まる MX\*.py プログラムは <b>OpenMX</b>用
	5. <b>PW</b>から始まる PW\*.py プログラムは <b>Quantum ESPRESSO(PWScf)</b>用
	6. <b>R</b>から始まる R\*.py プログラムは <b>RMC_POT</b>用
	7. <b>V</b>から始まる V\*.py プログラムは <b>VASP</b>用
	8. <b>W</b>から始まる W\*.py プログラムは <b>WIEN2k</b>用
4. 先頭の大文字を除いて同じ名前だったらほぼ同じ操作で同じことが出来ます。
	1. (例) Vplot\_LDOS.py と Wplot\_LDOS.py は同じく LDOS 描画ツールでほぼ同じコマンドラインオプションで同じ描画をしてくれる機能を有します。
5. \*plot\*.py が含まれているコードは matplotlib を用いた2Dプロットかもしくは3Dプロットするコードです。

### いくつかの具体的なツールの説明
